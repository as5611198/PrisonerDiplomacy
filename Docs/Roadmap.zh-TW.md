# Prisoner Diplomacy 1.2 後續版本計畫書

[English](Roadmap.md) | [繁體中文](Roadmap.zh-TW.md)

狀態：觀察期與社群 QA。`1.2.0` 是目前正式公開基準。本文件記錄候選方向，不代表每一項都一定製作，也不保證版本編號永遠不調整。

## 一、目前決策：先讓子彈飛一會兒

在改動存檔 Schema、交易狀態機或公開寫入 API 以前，先讓 `1.2.0` 在真實玩家環境運作。

初始觀察期為正式公開或最後一個穩定性 Hotfix 後的 7 至 14 天。這段期間：

- 收集玩家 QA、相容性回報、自動錯誤簽章與本地化問題；
- 先重現、分類，再決定是否修正；
- 已確認的上線阻斷問題可以立即處理；
- 不因為某個點子很吸引人就立刻開大型功能分支；
- 未經完整設計，不改動已接受交易的語意與核心權威邊界。

若期間推出新的穩定性 Hotfix，觀察基準可以重新計算或延長。

## 二、什麼情況可以中斷觀察期？

以下任何一項只要確認可重現，就可以立即準備 `1.2.x` 修補：

- 存檔損壞、Pawn 遺失、報酬重複／未發放，或不可恢復的交易狀態錯誤；
- 正常支援流程會穩定出現紅字；
- 使用正式依賴與載入順序仍無法載入；
- 隱私、API Key、自動回報同意或外部服務隔離問題；
- 大量玩家無法接受、拒絕、釋放或關閉交易的 UI 阻斷；
- 可確認是 Prisoner Diplomacy 引起的相容性 Regression；
- 支援語言或 Workshop 套件因翻譯／包裝問題無法載入。

單純美術偏好、個人平衡意見與尚未重現的第三方衝突，先保留在 Triage，不直接變成 Hotfix。

## 三、觀察期要收集什麼？

不要只數留言數量，應該按錯誤簽章與可重現流程整理：

| 分類 | 需要的證據 |
| --- | --- |
| 交易 | 重複／未付款、失效 Deal、釋放、換俘、期限與派系儲備簽章 |
| 存檔安全 | 新存檔、舊存檔、Schema 遷移、移除模組與重新載入結果 |
| 擴展事件 | 中立交易點、假投降、審判、伏擊、重試與世界物件清理 |
| UI | 解析度、UI Scale、長翻譯、按鈕可達性與無俘虜派系瀏覽器 |
| 相容性 | Package ID、版本、載入順序、重現步驟與隔離後日誌 |
| 效能 | 大量派系／俘虜、定期掃描、UI 更新與 Log Spam |
| API/Add-on | 註冊失敗、缺少的真實用例、作者被迫使用的不安全繞路 |
| AI／錯誤回報 | 同意、去識別、Timeout、過期回覆、Provider 隔離與修復結果 |

訂閱數本身不是開發門檻。幾份完整、可重現的報告，比大量模糊印象更有價值。

## 四、版本規劃

### 1.2.1 與後續 1.2.x：只做穩定化

允許範圍：

- 已確認 Bug 與相容性修正；
- 翻譯、Workshop Metadata、文件與新手教學修正；
- 診斷與重現工具；
- 不改變結果的效能改善；
- Fail-closed 驗證與更清楚的錯誤訊息；
- 維持 Binary Compatibility 的唯讀 Snapshot 欄位。

1.2.x 應避免：

- 只為選用內容增加新存檔 Schema；
- 批次交易、新事件 Executor 或新的交易權威；
- 沒有遷移政策就改寫現有交易與平衡；
- 刪除或改名已公開的 API ID。

完成門檻：沒有未處理的已確認 P0/P1 Regression，沒有重複發生的嚴重錯誤簽章，且最終套件通過建置、本地化、靜態驗證、載入 Smoke 與受影響人工流程。

### 1.3.0：受驗證的公開事件請求 API

主要目標：補上 API 1.2 最大缺口。現在外部事件定義只是可發現 Metadata，第三方不能透過公開契約請求排程。

建議範圍：

1. 提供 Capability 查詢，例如 `event-request-v1`，Add-on 不需要只猜版本字串。
2. 新增不可變的 `PrisonerDiplomacyEventRequest`，包含穩定 Definition ID、派系／俘虜／來源 Deal、觸發時間窗與 Add-on 去重 Key。
3. 公開受驗證的 Request 方法，回傳型別化結果與 Reason Key，不暴露內部 Scheduler。
4. 第一階段只允許已註冊 Definition 與核心擁有的四種事件家族。
5. 寫入前驗證 Pawn、派系、Deal、事件衝突、期限、重複 Key 與可存檔參考。
6. 核心成功 Commit 後，才提供唯讀 Event Snapshot 與生命週期通知。
7. Add-on Observer 發生例外時必須隔離，不得回滾或重新解釋已完成核心結果。
8. API Inspector 顯示 Capability、註冊與衝突診斷。
9. Example Add-on 增加一個明確的開發者測試排程，不在一般遊戲自動洗事件。
10. 同步 API 1.3 文件、遷移說明、範本與確定性 Smoke。

第一版明確不做：

- 可以任意修改 Pawn、Deal、報酬、派系記憶或核心存檔清單的 Callback；
- 反射 `PrisonerDiplomacyGameComponent`；
- 尚未看到已 Commit 的 `Completed` Snapshot 就宣告完成；
- 在核心交易內執行無限制的自訂結果程式碼；
- 讓 AI 決定事件或報酬是否成立。

Phase B 只有在公開 Request API 穩定後才考慮：有限 Eligibility Provider、翻譯選項 Metadata，以及一小組受驗證的 Outcome Command。完全自訂事件仍應由 Add-on 自己的 GameComponent 管理。

開始開發門檻：

- `1.2` 至少連續七天沒有未處理的已確認 P0/P1；
- 上線後重複出現的錯誤簽章已經理解或修掉；
- 至少有兩個具體 Add-on 用例可以驗證 Request 欄位與生命週期；
- API 規格已寫出存檔／讀檔、去重、取消、重試、所有權與失敗語意；
- Example Add-on 可以完全透過公開 API 測試，不需要私有呼叫。

驗收門檻：

- 重複請求不會建立重複事件或結果；
- 無效／過期 Request 不改變遊戲狀態；
- 存檔讀檔保留事件 ID 與所有權；
- Add-on 被移除或發生錯誤時，不會卡死核心交易；
- Observer 例外被隔離；
- API 1.2 Add-on 仍可註冊；
- Core-only 與 Core + Example Add-on 都通過 Smoke 與人工事件流程。

### 1.3.x：深化外交歷史與協議中心

目前派系瀏覽器已經有協議、歷史與事件頁，不再新增另一個互相競爭的視窗，而是深化現有介面：

- 統一時間順序的派系外交 Timeline；
- 依派系、俘虜、Deal、協議與事件類型篩選；
- 顯示要求、談妥、實際發放、失敗與退款明細；
- 停火與情報剩餘時間的歷史；
- 好感與派系記憶的因果摘要；
- 長期存檔的保留／歸檔政策；
- 不包含私人文字與憑證的可複製診斷摘要。

這部分保持唯讀，不改變交易計算結果。

### 1.4.0 候選：多俘虜／批次交涉

候選內容：

- 一份提案包含多名俘虜；
- 多名俘虜交換一名高價值人質；
- 派系主動提出整批釋放條件；
- 每名 Pawn 價值明細與總預算；
- 明確定義原子完成或部分完成；
- 其中一名死亡、逃脫、轉移或失效時的安全結果；
- 群組交易的報酬、退款與 Exactly-once；
- 新存檔遷移與大量清單 UI 可用性。

這需要新的狀態模型，不能只在現有 `PrisonerDeal` 塞一個 Pawn List。開始寫程式以前必須先決定 ID、所有權、部分成功、釋放順序、期限延長與回滾語意。

### 1.5.0 候選：Special Reward API 2.0

候選內容：

- 型別化的種族／派系專屬 Reward Provider；
- 多個固定候選報酬，仍由核心控制選擇與驗證；
- 品質、材質、基因包、植入物、研究資料等有限 Descriptor；
- 明確的價值計算與最大數量契約；
- 缺少來源 Mod 或 ThingDef 被移除時的後備政策；
- Capability Discovery 與 API 1.x 相容性；
- Example Add-on 同時示範 Vanilla 與一個選配種族／派系整合。

核心仍負責價值、儲備、物資上限、存檔、發放與 Exactly-once。Provider 不得自行 Spawn 或 Reserve 物品。

### 更後期候選：AI 長期外交記憶

可能內容：

- 保存最近幾次交涉的精簡摘要；
- 引用過去威脅、讓步、毀約與善待；
- 定義核心 Persona、Add-on Persona 與玩家 Override 的合併順序；
- 顯示最終 Sanitized Context 預覽；
- 確定性離線模板與過期 Request 取消。

AI 仍以敘事為主，只能回傳經驗證的有限 Signal；不得自由決定最終報酬、執行事件、重寫已接受 Deal 或成為派系記憶權威來源。

## 六、明確延後

- 讓 AI 自由決定最終白銀、好感、物資、停火與情報數字；
- 可繞過核心驗證直接接受、完成或取消 Deal 的公開方法；
- 在核心交易內執行任意 Add-on 寫入 Callback；
- 只看到別的模組名稱，尚未重現就製作相容 Patch；
- 沒有獨立專案就承諾 Multiplayer 相容；
- 在初始觀察期進行大型平衡改版。

## 七、觀察期結束時怎麼決定？

維護一份統一 Triage 表，至少包含：

- 錯誤簽章或 Issue ID；
- 嚴重程度與受影響版本；
- 是否可重現；
- 存檔、Log、Mod List 證據；
- 負責人與下一步；
- 目標版本或延後原因。

觀察期結束後只做一個明確決定：

1. 發布 `1.2.1`；
2. 因基準改變而延長觀察；
3. 凍結 `1.2` 功能並開始 `1.3` API 規格；
4. 證據不足，繼續延後新功能。

證據改變時再修改本計畫。不要默默把「候選」變成「已承諾開發」。
